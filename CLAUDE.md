# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository status

The repository holds five static tools for Apostello Comm, plus this documentation. No build system, package manifest, or test suite anywhere — plain HTML/CSS/JS with zero dependencies throughout. Three of the five tools (newsletter generator, Instagram calendar generator, and the newsletter intake form) share their core generation logic via plain `<script>`-tag modules under `/shared/` — see "Shared JS modules" below — rather than duplicating it; the registration form and site generator's own generation logic remains standalone. All five tools do, however, now share the same backend-connectivity layer (`apocomm-config.js`/`apocomm-backend.js`, see "Shared Google Sheets backend" below) — every tool that reads or writes client/intake data talks to one shared Google Sheet through a small Apps Script Web App, with `localStorage` demoted from source of truth to an offline fallback cache.

Run either tool locally with any static file server, e.g. `python3 -m http.server 8000` from the repo root, then open the relevant path below. There is no build or lint step. There is no automated test suite; verify changes by exercising the tool in a browser (or headless via Playwright, already available in this environment).

## Repository layout (GitHub Pages)

The repo root is served directly by GitHub Pages, so the layout separates internal tools from public content:

- `/index.html` — a plain-text landing page linking to all 5 tools below. Internal use only, not meant to be shared with missionaries.
- `/admin/registration/`, `/admin/site-generator/`, `/admin/newsletter/`, `/admin/instagram-calendar/` — the staff-facing tools (see Architecture below). `newsletter-intake/` (filled out by missionaries monthly, not staff) stays at the repo root rather than under `/admin/`, since it's a link handed directly to missionaries rather than something staff navigate to.
- `/shared/` — `apocomm-config.js`, `apocomm-backend.js`, `apocomm-common.js`, `newsletter-core.js`, `instagram-core.js`. The first two (config + backend client) are loaded by all 5 tools, wiring them to the shared Google Sheets backend (see "Shared Google Sheets backend" below); the latter three carry the generation logic shared between the newsletter generator, Instagram calendar generator, and the newsletter intake form's automated dual-generation flow (see "Shared JS modules" below). Not served as a standalone tool itself, just loaded via `<script>` tags before each consuming tool's own `app.js`.
- `/sites/<ClientID>/index.html` — the actual public output: one self-contained HTML file per missionary, generated by the site generator and committed here manually. Nothing under `/sites/` is generated automatically; see `sites/README.md` for the convention.

### Registration form (`admin/registration/index.html`, `admin/registration/style.css`, `admin/registration/app.js`)

Captures a missionary's self-registration and outputs a 36-column TSV row.

- `index.html` — the form markup. Field `id`/`name` attributes match the TSV column names used by `app.js`; checkbox groups (`RequestedServices`, `Channels`) share a `name` and are read via `querySelectorAll`.
- `app.js` — all logic, in one IIFE:
  - `REQUIRED_TEXT_FIELDS` / `REQUIRED_GROUP_FIELDS` define what blocks submission; `validate()` enforces them and writes inline errors.
  - `analyzeSecurity()` scans `MissionSummary` against `SECURITY_KEYWORDS` (phrases implying a need for discretion) to set `SecuritySensitive`. When `YES`, `SecurityInstructions` is left blank for a human to fill, and the UI shows a blocking security notice — this mirrors the security-first rule in the `apostello-onboarding` skill.
  - `nextClientId()` generates `APC-YYYY-000` by incrementing a per-year counter in `localStorage` under `apocomm_seq_<year>` — there is no backend, so this is a client-only sequence, not a durable/shared one. Deliberately *not* prefixed `apocomm_client_`, since that prefix is reserved for saved client rows (see "Shared localStorage" below) and is scanned by the other tools' "load saved client" dropdowns.
  - `completionStats()` computes completion across the 17 required fields (the 16 form-required fields plus the always-derived `SecuritySensitive`), matching the `%_Complétude` concept from the spreadsheet this data is destined for.
  - `buildRow()` / `TSV_COLUMNS` (`TSV_COLUMNS` is just `ApoComm.REG_COLUMNS`, not a local duplicate) assemble the 36-column tab-separated row, in the exact column order the destination spreadsheet expects. `sanitize()` strips tabs/newlines from every value so the TSV can't be corrupted by free-text input.
- On submit, `ApoComm.registerClientRemote(values)` (shared, see "Shared Google Sheets backend" below) always caches the row locally first, then writes through to the backend's `registerClient` action. `#save-status` reports which happened: "Saved as `<ClientID>` to the shared database — available to the other tools everywhere" on success, or a `.warning`-styled message ("Could not reach the shared database — saved locally only...") if the backend write failed — the local copy is never lost either way. There is intentionally no Gmail integration here — see domain context below for where that logic lives conceptually.

### Site generator (`admin/site-generator/index.html`, `admin/site-generator/style.css`, `admin/site-generator/app.js`)

Takes one pasted 36-column TSV row (the same format the registration form produces) and generates a single self-contained HTML file — a one-page public site for that missionary.

- `parseRow()` splits on the first non-blank line, then on `\t`; it deliberately does not `.trim()` the whole line before splitting, since trailing empty columns (e.g. `Notes` blank) end the row in real tab characters that a blanket trim would eat, undercounting columns.
- `evaluateSecurityGate()` is the security gate, checked before anything is generated: `SecuritySensitive = YES` with empty `SecurityInstructions` blocks generation outright (no preview, no decision summary — nothing rendered). `YES` with instructions present generates the site but treats `SecurityInstructions` as an allow-list for `CountryOfService`/`CityOfService`, evaluated by `isLocationFieldAllowed()`.
- `isLocationFieldAllowed()` reads `SecurityInstructions` clause by clause (split on `.`/`;`/newline). A clause permits `country` or `city` only if it contains the keyword plus an explicit allow word (`ok`, `allowed`, `share`, `publish`, ...) with no negation word (`not`, `never`, `don't`, ...) in that same clause. Silence or ambiguity defaults to hidden — this is the safety-critical piece, so precision was favored over cleverness.
- `buildSiteHtml()` assembles the output document, escaping every interpolated value via `escapeHtml()` (the generated page is real HTML served to the public, so free-text fields like `MissionSummary` must not be able to inject markup/scripts). The `Email` field is never printed as visible text — only used inside a `mailto:` href behind a generic "Get in touch" label.
- The photo section is three placeholder `.photo-slot` divs, each preceded by an HTML comment (`<!-- PHOTO n: replace... -->`) marking where to paste a real `<img>` later.
- `SITE_CSS` is inlined into the generated page's `<style>` tag so the output is a single portable file with no external requests (no font/CDN loads).
- The generator UI shows a `security-decision` summary (SecuritySensitive value, and whether country/city will be shown) so a human can audit the gate's decision before trusting or publishing the output.
- After generation, a `save-path-instruction` line tells the operator exactly where to commit the file: `/sites/<ClientID>/index.html`. The download button's suggested filename is `index.html` to match — the browser can't write into a repo subfolder directly, so this is instructional text plus a conveniently-named download, not an automated commit.
- `toFirstPerson()` rewrites `MissionSummary`/`MainObjective` (which are typically captured in third person by staff — see `apostello-onboarding`) into first-person singular before they're shown on the public page, since the site is meant to read in the missionary's own voice. It's a deterministic rule-based pass (name/pronoun substitution, verb-form fixes for common auxiliaries), not NLP — good enough for the patterns this data actually contains, but a construction it doesn't recognize (e.g. the missionary's name as a verb's object with no preceding preposition) can slip through unconverted. Duplicated verbatim in the newsletter generator rather than shared, consistent with this tool's standalone generation logic.
- The client-search lookup (`#client-search`, see "Client lookup by name" below) is the one part of this tool that isn't standalone: it calls `ApoComm.searchClients()`/`ApoComm.fetchClientRow()` (shared, see "Shared Google Sheets backend" below) rather than reading `localStorage` directly, same as the newsletter/Instagram/intake tools.

### Monthly newsletter intake (`newsletter-intake/index.html`, `newsletter-intake/style.css`, `newsletter-intake/app.js`)

Short recurring form a missionary fills out each month. Beyond capturing the 10-column intake row, submitting this form now **automatically generates that month's newsletter and Instagram calendar in place** — no navigating to the other two tools, no manual paste. The raw TSV row is still shown after submit (for re-pasting into the standalone tools later, e.g. to regenerate a past month), but it's no longer the primary output.

- Fields: `ClientID`, `IsFirstNewsletter`, `Events` (list), `MeetingsSummary` (free text rollup, not itemized), `PrayerNeeds` (list), `UpcomingProjects` (list), `NumbersUpdate` (free text), `NewPhotoLinks`, `AnythingToAvoid`. `SubmissionDate` (today's date) is appended as a 10th, system-derived column, same reason as before (tells later intakes for the same `ClientID` apart).
- Required fields are `ClientID`, `IsFirstNewsletter`, and at least one `Events` entry — everything else is optional, so a very light month (one event, nothing else) is a valid submission, not an error.
- `Events`/`PrayerNeeds`/`UpcomingProjects` are variable-length lists: the missionary can enter any number of entries (including zero for the two optional ones), one per line or semicolon-separated — `sanitizeList()` normalizes either input style into a single `; `-joined TSV cell so the generators only ever have to split on `;`.
- `#client-search` above the `ClientID` field is the same name-based lookup combobox as the three admin tools (see "Client lookup by name" below) — selecting a name fills the `ClientID` field, which stays the field validation/submission actually reads. Missionaries who know their own Client ID (it's on their registration confirmation) can also just type it directly; the search box is a convenience, not a requirement, matching the fallback pattern used elsewhere.
- **On submit**, after the existing field validation passes: `ApoComm.fetchClientRow(ClientID)` (shared, see "Shared Google Sheets backend" below) looks up the matching registration row — backend `getClient` first, falling back to the local cache only if the backend is unreachable. This is what lets a missionary submit from a browser that has never talked to any Apostello Comm tool before, as long as the backend has their record. If no registration is found anywhere (backend genuinely has no such `ClientID`, and nothing local either), generation stops immediately with "No registration profile found for this client. Load or paste it first." — no newsletter, no Instagram calendar, no partial output from incomplete data. If found, the intake row is saved (`ApoComm.saveIntakeRemote()`, writing through to the backend's `saveIntake` action in addition to the local cache), then the security gate is evaluated against the registration row: `SecuritySensitive = YES` with empty `SecurityInstructions` blocks *both* outputs together with the same message the standalone tools use — nothing is generated for either channel. Otherwise `ApoComm.Newsletter.build()` and `ApoComm.Instagram.build()` (the latter wrapped in try/catch, since `checkLanguagePurity()` can throw) run back-to-back against the same `regFields`/`intakeFields`, and both results render on the same page in clearly separated "Newsletter" and "Instagram content calendar" sections, each with its own copy button(s) — see "Shared JS modules" below for where this generation logic actually lives.

### Newsletter generator (`admin/newsletter/index.html`, `admin/newsletter/style.css`, `admin/newsletter/app.js`)

Takes one 36-column registration row and one 10-column intake row, and drafts a plain-text subject + body for that month's newsletter, ready to paste into Mailchimp's Campaign Builder. All generation logic lives in `shared/newsletter-core.js` as `ApoComm.Newsletter` (see "Shared JS modules" below); this tool's own `app.js` is now just the client-search/month-select UI wiring (backend-first, via `ApoComm.searchClients()`/`ApoComm.fetchClientRow()`/`ApoComm.fetchIntakeMonths()`/`ApoComm.fetchIntakeRow()` — see "Shared Google Sheets backend" below) plus calls into `ApoComm.Newsletter.evaluateSecurityGate()` / `.build()`.

- Reuses the registration form's security gate concept (`ApoComm.evaluateSecurityGate()`, shared): `SecuritySensitive = YES` with empty `SecurityInstructions` blocks generation outright, same message as the site generator.
- Extends the site generator's clause-scanning allow-list (`ApoComm.isTopicAllowed()`, generalized from `isLocationFieldAllowed()`) to six topics: `intro` (the `MissionSummary`/`DepartureDate` used in a first newsletter), `highlights` (`Events`+`MeetingsSummary`), `prayer` (`PrayerNeeds`), `looking_ahead` (`UpcomingProjects`), `numbers`, and `whatsapp`. Each is included only if a `SecurityInstructions` clause explicitly permits it; otherwise the whole section is omitted (except `intro`/`whatsapp`, which swap to a fixed, non-specific line) rather than attempting any automated rewriting of the missionary's own words.
- Content is always exactly 4 fixed sections regardless of how many list items exist that month — "This Month's Highlights", "Prayer Needs", "Looking Ahead", "By the Numbers" — each skipped entirely (not padded) if its list is empty. `weaveItems()`/`buildSection()` weave any number of real list items (each kept verbatim after `ApoComm.toFirstPerson()`) into one flowing passage using a rotating bank of fixed lead-in connectors (`CONNECTORS`, e.g. "On top of that: ", "Around the same time: ") — never an itemized "first... second..." list. The anti-fabrication rule applies per *section*, not per item: real material is woven together first, and only if the section is still under `MIN_EXPANSION_WORDS` does the same generic reflection-bank top-up from before (now including a fourth, `looking_ahead` bank) kick in, with the same `FALLBACK_COMMENT` marker if a section still can't honestly reach 150 words.
- `ApoComm.applyAvoidList()` (shared) is a second, independent redaction pass that always runs, regardless of `SecuritySensitive`: it splits the intake's `AnythingToAvoid` into clauses and case-insensitively strips any that appear verbatim in the assembled subject/body. This is a literal-substring safety net, not an NLP filter — it catches the common case (a missionary names an exact word/phrase to avoid) but won't catch a paraphrase of it.
- Content and template chrome (labels, intro/CTA phrasing, sign-off) are localized to `PrimaryLanguage` via a small `TEMPLATES` dictionary (English/French/Spanish/Portuguese, detected by `ApoComm.detectLanguage()`, defaulting to English). The missionary's own free text is never machine-translated — only the surrounding scaffolding changes language.
- If the registration and intake rows carry different `ClientID`s, a non-blocking `mismatch-warning` banner fires — this doesn't block generation (unlike the security gate) since a human is expected to read and correct it before sending. (The automated intake flow can't hit this case: it looks up the registration row *by* the intake row's own `ClientID`, so the two can never disagree.)
- The `security-decision` panel lists, per topic, whether it was included or omitted, plus per-section word counts and which `AnythingToAvoid` terms were found and stripped — the same audit-before-publish pattern as the site generator.
- The whole newsletter reads in the missionary's own first-person voice: template chrome is hand-written in first person per language; every list item and free-text field is passed through `ApoComm.toFirstPerson()` before being woven in. Subject lines and the sign-off name are left as a name (third person there is expected — a reader needs to know whose update they're opening).

### Instagram content calendar generator (`admin/instagram-calendar/index.html`, `admin/instagram-calendar/style.css`, `admin/instagram-calendar/app.js`)

There was no prior "Instagram generator" in this repo — this tool was built from scratch to this spec. It reuses the exact same two inputs as the newsletter generator (36-column registration row + 10-column monthly intake row, no new form) and turns the monthly pool of real items into a 4-week, ~16-post Instagram calendar — a different format of the same material, not a separate content stream. All generation logic lives in `shared/instagram-core.js` as `ApoComm.Instagram` (see "Shared JS modules" below); this tool's own `app.js` is just UI wiring, including the same backend-first client-search/month-select pattern as the newsletter generator (see "Shared Google Sheets backend" below).

- Parsing, the security gate/`isTopicAllowed()`, `applyAvoidList()`, and `toFirstPerson()` are shared with the newsletter generator via `shared/apocomm-common.js` rather than duplicated (this was previously duplicated verbatim — see "Shared JS modules" below for why that changed). Four topics are gated here (`highlights`, `prayer`, `looking_ahead`, `numbers` — no `intro`/`whatsapp`, since this tool has neither); `MeetingsSummary` rides on the `highlights` allow-flag, same as in the newsletter.
- **The topic pool is dynamic, not fixed.** `buildItemsByCategory()` expands `Events`/`PrayerNeeds`/`UpcomingProjects` into one pool entry *per list item* (plus one entry each for `NumbersUpdate` and `MeetingsSummary` if present) — a month with 4 events and 3 prayer needs has 7+ distinct real topics to draw from, not 3. `buildPool()` interleaves categories round-robin so even the earliest slice of the calendar already mixes topics.
- `FORMAT_PREFERENCE` defines, per category, an ordered list of compatible formats out of the 7-format library. `prayer_focused` is the one hard exclusivity rule from the spec (prayer only); every other format is open to any category. Each pool item's list is also *rotated by its own index within the category* (`rotateList()`) — without this, every item in a multi-item category would share the same #1 format (four Events would all open with the identical "Behind-the-Scenes" framing text); rotating means four Events instead lead with four different formats.
- `buildWaves()` is the scheduler: wave 0 gives every distinct pool item its own single best-fit format (maximum variety first — this is "draw from the expanded real pool before falling back to multiple-angle recycling"), wave 1 gives items that still have an unused format a second angle, and so on. Target is `min(16, wave count)`; a richer month (more real items) fills more of the calendar straight from wave 0, so it reads as more varied, not more repetitive. If waves run out before 16 slots are filled, the shortfall is real and the output ends with `<!-- Topic exhausted without fabrication risk -->` instead of padding or recycling further — verified by a test that limits input to a single Event (capacity 6) and confirms the flag fires at exactly 6 posts.
- Caption templates (`TEMPLATES.english`, keyed by category then format) never introduce a new fact, number, name, date, or event — each one wraps the missionary's own unaltered (already first-person) sentence in fixed framing text. `meetings` reuses the `numbers` template set (both are single rollup stats) rather than duplicating near-identical content. French/Spanish/Portuguese use `GENERIC_TEMPLATES` instead — one template per format, shared across all categories — a deliberate scope cut kept from the original build.
- `checkLanguagePurity()` is a defensive per-post check run before a caption is ever added to the calendar: for an English profile it rejects any generated caption whose *template-authored framing* (the missionary's own seed sentence is deliberately excluded from the check, isolated via `caption.split(seed)`) contains non-English accented characters; for a non-English profile it rejects stray English telltale phrases. `detectLanguage()` already reads `PrimaryLanguage` from the parsed registration row and nothing else — there is no code path through which session or conversation context could influence it — so this check exists as a regression guard, not a fix for a located bug.
- `GRAPHIC_NOTES` and `HASHTAG_BANK` are keyed by format/category only, not language — both are either operator-facing instructions (graphic direction) or hashtags that conventionally cross language boundaries on Instagram regardless of caption language, so one English set is reused everywhere rather than translating four times.
- Output renders as both a visual calendar (`calendar-view`, grouped by week, one card per post showing topic label — e.g. "Event 2", "Prayer Need 1" — format/caption/hashtags/graphic note) and a plain-text export (`calendar-output`) for pasting into a planner; `AnythingToAvoid` is applied per-caption so both views stay consistent, and the `security-decision` panel lists posts generated vs. target, pool size, which formats were used per category, and any avoid-list terms stripped.

## Shared JS modules (`/shared/`)

The newsletter generator, Instagram calendar generator, and the newsletter intake form's automated dual-generation flow all need the same generation logic (registration/intake TSV parsing, the security-gate clause-scanner, `AnythingToAvoid` redaction, first-person conversion, language detection, HTML escaping, and the shared-localStorage client lookup), plus each generator's own topic set and build routine. Rather than a fourth copy-paste (or asking the intake page to reach into the standalone tools' `app.js` files), this logic was extracted into three plain `<script>`-loaded modules — no bundler, no build step, consistent with the rest of this repo — each attaching to a single global, `window.ApoComm`:

- `shared/apocomm-common.js` — tool-agnostic infrastructure: `ApoComm.REG_COLUMNS`/`INTAKE_COLUMNS`, `ApoComm.parseRow()`, `ApoComm.evaluateSecurityGate(regFields, topics)` (the clause-scanning blocking decision, generalized to take a `{topicKey: [keywords]}` map so callers with different topic sets share one implementation — see below), `ApoComm.isTopicAllowed()`, `ApoComm.applyAvoidList()`, `ApoComm.toFirstPerson()`, `ApoComm.detectLanguage()`, `ApoComm.escapeHtml()`, the local-cache functions (`ApoComm.listSavedClients()`, `ApoComm.getSavedClientRow()`, `ApoComm.listSavedMonths()`, `ApoComm.saveIntakeRow()`, `ApoComm.cacheClientRow()`), and the backend-first orchestration layer built on top of them (`ApoComm.searchClients()`, `ApoComm.fetchClientRow()`, etc.) — see "Shared Google Sheets backend" below for that whole layer.
- `shared/newsletter-core.js` — everything newsletter-specific, exposed as `ApoComm.Newsletter`: its 6-key `TOPICS` map, `evaluateSecurityGate()` (a thin wrapper calling the common one with `Newsletter.TOPICS`), the four-language `TEMPLATES`/`EXPANSION_BANKS`/`CONNECTORS` dictionaries, paragraph weaving/expansion, and `build(regFields, intakeFields, security)` — the core generator, unchanged in behavior from before the extraction.
- `shared/instagram-core.js` — everything Instagram-specific, exposed as `ApoComm.Instagram`: its 4-key `TOPICS` map, `evaluateSecurityGate()`, the format/caption/hashtag libraries, `checkLanguagePurity()`, the pool/wave scheduler, `build()` (the core generator), `renderHtml()`/`renderText()`, and `showDecisionLines()` (returns the audit-panel HTML lines as an array rather than writing to a specific DOM node, since the standalone tool and the intake page each have their own `security-decision` element to fill).
- Both `admin/newsletter/index.html` and `admin/instagram-calendar/index.html` load `apocomm-common.js` then their own core module before `app.js`; `newsletter-intake/index.html` loads all three (it needs both generators). Each tool's own `app.js` now contains only DOM wiring (client-search combobox, month-select, form/button handlers) and calls into `ApoComm.*`/`ApoComm.Newsletter.*`/`ApoComm.Instagram.*` — no generation logic is duplicated in any `app.js` anymore. The registration form and site generator are unchanged and still fully standalone (out of scope for this extraction — they don't share a topic-gated generator with anything else).
- Generalizing `evaluateSecurityGate()` to accept a `topics` parameter (rather than two separate hardcoded copies) is what lets the intake form's automated flow check the block/no-block decision once and have it apply identically to both outputs: the decision itself (`SecuritySensitive`/`SecurityInstructions` on the registration row) never depends on which topic set is passed in, only each generator's per-topic *allow* map does — so `Newsletter.evaluateSecurityGate()` and `Instagram.evaluateSecurityGate()` always agree on blocked/not-blocked for the same registration row, even though they're called separately to get their differently-shaped allow maps.

## Shared Google Sheets backend

All 5 tools talk to one shared Google Sheet (client records in a "Fiches" tab, monthly intakes in a "Monthly_Intakes" tab) through a small Apps Script Web App, rather than each browser only knowing what's been saved locally. `localStorage` is no longer the source of truth — it's now purely an **offline fallback cache**: every write goes to both the backend and the local cache, and every read tries the backend first and only falls back to the local cache if the backend is unreachable.

- `shared/apocomm-config.js` — the single place the Web App URL and API key are configured (`ApoComm.CONFIG.WEB_APP_URL` / `ApoComm.CONFIG.API_KEY`). Every tool loads this before `apocomm-backend.js`; nothing else in the codebase hardcodes either value.
- `shared/apocomm-backend.js` — `ApoComm.Backend`, a thin GET-only client for the six actions (`searchByName`, `getClient`, `registerClient`, `getIntake`, `saveIntake`, `listIntakeMonths`) — this API has no POST; writes are GET requests carrying a URL-encoded JSON array in a `data` param. Every function resolves to `{ok, ...}`; `ok: false` means a genuine transport failure (network error, non-2xx HTTP, unparseable body) — reachable-but-empty/not-found responses (`null`, `[]`, `{error: ...}`, etc.) resolve as `ok: true` with an empty/null payload instead, so callers can tell "the database is down" apart from "the database has no such record" (see `looksEmpty()`/`asRow()`/`asList()` in that file). **This module could not be exercised against the real deployed backend while writing it** — this sandbox's network egress policy blocks `script.google.com` outright — so its response-shape handling is written defensively against what the API description implies (bare JSON array for a single row, bare array of rows for a list) with tolerance for a few common envelope variations; if the live backend's actual shape differs, `looksEmpty`/`asRow`/`asList`/`entryToRegFields` are the functions to adjust; every caller elsewhere in the codebase consumes the already-normalized `{ok, ...}` result and shouldn't need to change.
- `shared/apocomm-common.js` adds the orchestration layer on top: `ApoComm.searchClients(query)`, `ApoComm.fetchClientRow(clientId)`, `ApoComm.registerClientRemote(fields)`, `ApoComm.saveIntakeRemote(intakeFields)`, `ApoComm.fetchIntakeMonths(clientId)`, `ApoComm.fetchIntakeRow(clientId, month)` — each tries the backend first, refreshes the local cache on a successful read, and falls back to the local cache (with `warning: "Could not reach the shared database — using local data only."`) only on a genuine transport failure. `ApoComm.searchClients()` additionally falls back to the local cache when the backend is reachable but returns zero matches (this browser may hold a client registered while offline that hasn't synced yet). Also here: `ApoComm.regFieldsToBackendRow()`/`backendRowToRegFields()` and `ApoComm.intakeFieldsToBackendRow()`/`backendRowToIntakeFields()` convert between the `fields` object every generator already works with and the backend's JSON-array row shape; `ApoComm.cacheClientRow()` writes the local TSV cache (called after every successful backend read *and* write, so the cache never goes stale while the backend is reachable); `ApoComm.BACKEND_INTAKE_COLUMNS` is the backend's 11-value intake row shape — the same 10 local `INTAKE_COLUMNS` plus an explicit `Month` (`YYYY-MM`, derived from `SubmissionDate`) column, since that's what `getIntake`/`listIntakeMonths` index by.
- Every tool's UI layer calls these orchestration functions instead of reading `localStorage` directly, and shows `result.warning` (when present) in a `#backend-warning` element styled consistently across all 5 tools' stylesheets. Client-search results and the "load a past month" selects are rendered asynchronously with a request-token guard (`searchToken`/`monthToken`, incremented per call, stale responses discarded) so a fast typist or fast client-switch never has an old response clobber a newer one.
- The registration form's `nextClientId()` (the `APC-YYYY-000` counter) is unchanged and still purely local — the backend API described here has no ID-allocation action, so two browsers registering in the same year can in principle generate the same `ClientID` before either syncs. Out of scope for this integration; flagged here as a known limitation rather than silently worked around.
- **Verifying this against the real backend**: this environment could not reach `script.google.com` to test live, so integration correctness was verified by mocking `ApoComm.Backend`'s HTTP calls (Playwright `page.route()`) against an in-memory fake "sheet" shared across separate browser contexts — covering: registration write-through, a fresh browser (empty `localStorage`) finding and loading a client by name, the full intake→dual-generation flow using only backend data, backend-down fallback-with-warning, a genuinely-unregistered `ClientID` producing the clean "not found" message without a false connectivity warning, and the security-block case sourced entirely from backend data. All passed against the mocked contract; the real deployment should be smoke-tested against the scenarios in the task this was built for before relying on it.

## Shared localStorage across tools

All 5 tools are served from the same GitHub Pages origin, so `localStorage` is naturally shared between them in a given browser. Since the Google Sheets backend integration above, this is no longer the source of truth for client/intake data — it's an **offline fallback cache**, kept warm by every successful backend read and write (see "Shared Google Sheets backend" above) and consulted only when the backend can't be reached. Two key conventions, used consistently across `admin/registration`, `admin/site-generator`, `admin/newsletter`, `admin/instagram-calendar`, and `newsletter-intake`:

- `apocomm_client_<ClientID>` — a cached 36-column registration TSV row. Written by `ApoComm.cacheClientRow()` after any successful `registerClient` write or `getClient`/`searchByName` read. Manual TSV paste still works exactly as before on the three admin tools that have a textarea — the lookup (backend or cache) is a convenience, not a requirement.
- `apocomm_client_<ClientID>_intake_<YYYY-MM>` — a cached 10-column monthly intake row, keyed by month. Written by `ApoComm.saveIntakeRow()`, called both directly (as the local half of `ApoComm.saveIntakeRemote()`, from the newsletter/Instagram/intake tools right after a save) using the intake row's *own* `ClientID`/`SubmissionDate` (not necessarily whatever is currently in the registration textarea, in case of a `mismatch-warning`). The newsletter/Instagram tools' "Load a past month's intake" `<select>` is populated via `ApoComm.fetchIntakeMonths()` (backend `listIntakeMonths`, merged with any local-only months) whenever the registration textarea changes (`regInput.addEventListener("input", refreshMonthSelect)`).
- The client-id scan (`ApoComm.listSavedClients()`, the local-only half of `ApoComm.searchClients()`) explicitly excludes any key matching `..._intake_\d{4}-\d{2}$` so a saved intake month never shows up masquerading as a client — this is also why `nextClientId()`'s counter key lives outside the `apocomm_client_` namespace entirely (see above); a bug where it briefly didn't caused a bogus `"seq_2026"` entry to appear in every "load saved client" list.
- None of this touches generation logic or security gates — it only pre-fills the same textareas/fields a human would otherwise paste into by hand, so every existing security/validation path runs unchanged regardless of whether the input came from the backend, the local cache, or a manual paste.

### Client lookup by name (site generator, newsletter, Instagram, newsletter intake)

The raw `ClientID` (`APC-YYYY-000`) stays the canonical key everywhere it matters (storage keys, the Sheet, the `apostello-onboarding` skill) but is never shown to the operator (or, on the intake form, the missionary) in these four tools — they search and select by name instead.

- `#client-search` is a text input, not a `<select>`: `ApoComm.searchClients(query)` (shared, backend-first — see "Shared Google Sheets backend" above) resolves to `{clients, source, warning}`, where each client is a `{clientId, firstName, lastName, country, label}` object. Focusing the empty input searches with an empty query (lists everyone the backend/cache has); typing re-searches live. This is async now (a network call, not a synchronous local read), so every tool's `renderClientResults()` shows a transient "Searching…" placeholder and guards against out-of-order responses with an incrementing `searchToken` — matching `renderClientResults()`, still duplicated per tool since each tool's DOM/result-wiring is slightly different (three fill a TSV textarea; the intake form fills the `ClientID` input directly).
- `ApoComm.assignDisambiguatedLabels()` (exported from `apocomm-common.js` so both the local-cache path and backend-sourced results share it) groups clients by identical "First Last" and appends a disambiguator only when needed: `(Country)` if every client in the group has a distinct, non-empty country, otherwise `(last 4 chars of ClientID)` as a guaranteed-unique fallback (e.g. two same-named clients in the same country).
- Selecting a result never trusts whatever the search step returned as the full record — it always calls `ApoComm.fetchClientRow(clientId)` (backend `getClient` first) to get the authoritative current row, per the explicit requirement that a stale/lighter search result shouldn't be what ends up driving generation. In the site generator/newsletter/Instagram tools this fills the registration textarea; on the intake form there's no textarea to fill — selecting a result instead writes `client.clientId` straight into the `#ClientID` field (the field the form actually validates/submits) and shows the label in the search box. In every case the actual `ClientID` only ever travels internally via a `clientMap` closure keyed by ID (never round-tripped through a DOM attribute as raw TSV, to avoid tab-character escaping edge cases).
- Two empty-state messages guide the user instead of a blank list: "No saved clients yet" (backend/cache has nothing at all) vs. "No match" (clients exist, none match the query) — both point at the fallback path (pasting the registration TSV row directly into the textarea below, on the three admin tools; typing the Client ID directly into the field below, on the intake form).

## Domain context

Apostello Comm is a communications agency serving missionaries. Client (missionary) records live in a Google Drive spreadsheet ("Apostello Comm — Base Missionnaires"), not in this repository. Operational rules for handling missionary client data (record format, required fields, security handling for missionaries in restricted-access countries, email drafting rules) are defined in the `apostello-onboarding` skill available in this environment — invoke it for any task involving missionary contacts, client records, or missionary-facing content, rather than improvising the process here.
