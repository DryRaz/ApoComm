# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository status

The repository holds five static tools for Apostello Comm, plus this documentation. No build system, package manifest, or test suite anywhere — plain HTML/CSS/JS with zero dependencies throughout. Three of the five tools (newsletter generator, Instagram calendar generator, and the newsletter intake form) share their core generation logic via plain `<script>`-tag modules under `/shared/` — see "Shared JS modules" below — rather than duplicating it; the registration form and site generator's own generation logic remains standalone. All five tools do, however, now share the same backend-connectivity layer (`apocomm-config.js`/`apocomm-backend.js`, see "Shared Google Sheets backend" below) — every tool that reads or writes client/intake data talks to one shared Google Sheet through a small Apps Script Web App, with `localStorage` demoted from source of truth to an offline fallback cache.

Run either tool locally with any static file server, e.g. `python3 -m http.server 8000` from the repo root, then open the relevant path below. There is no build or lint step. There is no automated test suite; verify changes by exercising the tool in a browser (or headless via Playwright, already available in this environment).

## Repository layout (GitHub Pages)

The repo root is served directly by GitHub Pages, so the layout separates internal tools from public content:

- `/index.html` — a landing page, internal use only, split into two labelled groups: the missionary-facing pages and the staff tools.
- **The folder a tool lives in states who fills it in.** `/registration/` and `/newsletter-intake/` sit at the repo root because a missionary fills them in themselves — registration once at signup, the intake every month — and both are links handed directly to a missionary. `/admin/site-generator/`, `/admin/newsletter/` and `/admin/instagram-calendar/` are staff tools and are not shared with missionaries. Registration was previously filed under `/admin/registration/` despite being self-registration written in the missionary's own voice; it moved to the root so the split is visible from the path alone, which matters because the two root paths are the ones that would go on a public custom domain. `/admin/registration/index.html` remains as a scriptless meta-refresh stub so links already handed out keep working — it carries no form and no backend configuration, and can be deleted once nothing points at it.
- `/shared/` — `apocomm-config.js`, `apocomm-backend.js`, `apocomm-common.js`, `newsletter-core.js`, `instagram-core.js`. The first two (config + backend client) are loaded by all 5 tools, wiring them to the shared Google Sheets backend (see "Shared Google Sheets backend" below); the latter three carry the generation logic shared between the newsletter generator, Instagram calendar generator, and the newsletter intake form's automated dual-generation flow (see "Shared JS modules" below). Not served as a standalone tool itself, just loaded via `<script>` tags before each consuming tool's own `app.js`.
- `/sites/<ClientID>/index.html` — the actual public output: one self-contained HTML file per missionary, generated by the site generator and committed here manually. Nothing under `/sites/` is generated automatically; see `sites/README.md` for the convention.

## Shared visual identity

Three of the five tools — registration, site generator, and newsletter intake — share a "correspondence" visual identity: warm paper/ink/ochre palette (`--paper #F7F3EA`, `--ink #2B3A55`, `--accent #C08A3E`, `--sage #7A8B76` for success, `--rust #B5533C` for errors), Fraunces (serif) for section/step headings only, Inter (sans) for every label/input/body of text. Each tool's `style.css` defines these as local custom properties (`:root { --paper: ...; }`) rather than a shared stylesheet — there's no `/shared/*.css` file, consistent with this repo's no-build-step approach; the four hex values are simply duplicated verbatim across the three files. Labels throughout are plain questions in the missionary's own voice ("Where will you be serving?" not "CountryOfService"); required fields carry a small pill (`.tag-required`) instead of an asterisk; validation errors stay in plain, non-blaming terms. Security-block/notice copy across these three tools is deliberately calm and reassuring while keeping the block itself firm and unambiguous — see each tool's own section below for exactly which string was reworded and why touching it doesn't change the underlying gate logic. **The newsletter generator and Instagram calendar generator were deliberately left out of this redesign** (not asked for) and keep their original blue-accent visual style — don't assume visual consistency extends to those two.

### Registration form (`registration/index.html`, `registration/style.css`, `registration/app.js`)

Captures a missionary's self-registration and outputs a 36-column TSV row. Filled in by the missionary, not by staff.

- `index.html` — a 6-step wizard (Identity, Mission, Audience, Needs, Content, Admin — one `<fieldset class="step">` per step, matching the Sheet's own field groupings) rather than one long page; a persistent step indicator up top shows all 6 by name with the current one highlighted and passed ones checked off, plus a live completion-percentage bar. Field `id`/`name` attributes still match the TSV column names used by `app.js` exactly (unchanged by the redesign — every field just lives inside a `.step` wrapper now instead of directly in the form); checkbox groups (`RequestedServices`, `Channels`) share a `name` and are read via `querySelectorAll`. Labels are phrased as plain questions ("Where will you be serving?" not "CountryOfService"); required fields carry a small `.tag-required` pill instead of an asterisk. All 6 steps are present in the DOM from page load (just hidden via the `hidden` attribute) — nothing is destroyed when navigating back, so no data is ever lost switching steps. Warm serif (Fraunces) is used only for step/section headings; every label, input, and body of text stays in the sans body face (Inter) so the form itself stays highly legible.
- `app.js` — all logic, in one IIFE:
  - The step-wizard layer (`STEP_NAMES`, `STEP_REQUIRED_TEXT`/`STEP_REQUIRED_GROUPS`, `validateStep()`, `renderStep()`, `goToStep()`, the live `updateProgress()`) is purely additive UI on top of the same single `<form>` — it reuses `validate()`/`buildRow()`/`completionStats()`/`setError()`/`clearErrors()` unchanged rather than duplicating their logic. `validateStep()` runs the same required-field checks as `validate()`, just filtered to the fields on the current step, so "Continue" can't be clicked past a required field without blocking the *submit-time* `validate()` from changing at all. `updateProgress()` calls the exact same `buildRow()`/`completionStats()` the result screen always used, just on every `input`/`change` event instead of once at the end, so the live progress bar and the final completion line can never disagree. If the final `validate()` (at actual submit, on the last step) ever finds an error on an earlier step — shouldn't normally happen since `validateStep()` already gated each step, but covers e.g. browser back/forward — `stepIndexForField()` brings that step back into view before scrolling to the field, rather than scrolling to a field hidden on an off-screen step.
  - `REQUIRED_TEXT_FIELDS` / `REQUIRED_GROUP_FIELDS` define what blocks submission; `validate()` enforces them and writes inline errors.
  - Missionary-facing, at the repo root (see layout above), loading `../shared/*.js`.
  - `Timezone` is a `<select>` of UTC offsets **labelled by country**, not a free-text box. The Dictionnaire specifies `UTC±X`, but almost nobody knows their own offset by heart, and the free field collected country names instead (two live rows read `Kenya`). Each option lists the countries on that offset and submits the `UTC±X` value, so the missionary picks the line with their country in it and the Sheet still gets the format it documents. Standard offsets only — daylight saving is not modelled, which is acceptable because the field only informs send/call scheduling. Being a `<select>` named `Timezone`, `form.elements.Timezone.value` reads it unchanged and `buildRow()` is untouched.
  - `PrimaryLanguage` is a two-option radio group (`English` / `French`) styled as a pair of buttons, not a free-text input — the whole content pipeline keys off this one value, and a free field produced values nothing downstream recognised, each silently falling back to English. The inputs stay real radios sharing the name `PrimaryLanguage`, so `form.elements.PrimaryLanguage.value` still returns the chosen value and `validate()`/`buildRow()`/`completionStats()` are untouched.
  - `analyzeSecurity()` scans `MissionSummary` against `SECURITY_KEYWORDS` (phrases implying a need for discretion) to set `SecuritySensitive`. When `YES`, `SecurityInstructions` is left blank for a human to fill, and the UI shows a blocking security notice — this mirrors the security-first rule in the `apostello-onboarding` skill.
  - `nextClientId()` generates `APC-YYYY-000` by incrementing a per-year counter in `localStorage` under `apocomm_seq_<year>`. This is now an **offline-only fallback**, used solely when the backend `registerClient` call fails outright — ClientID allocation is otherwise the backend's job (see below). Two browsers registering offline in the same year could in principle produce the same fallback ID before either syncs; an accepted limitation of a purely local counter, scoped to the already-degraded offline path. Deliberately *not* prefixed `apocomm_client_`, since that prefix is reserved for saved client rows (see "Shared localStorage" below) and is scanned by the other tools' "load saved client" dropdowns.
  - `completionStats()` computes completion across the 17 required fields (the 16 form-required fields plus the always-derived `SecuritySensitive`), matching the `%_Complétude` concept from the spreadsheet this data is destined for.
  - `buildRow()` / `TSV_COLUMNS` (`TSV_COLUMNS` is just `ApoComm.REG_COLUMNS`, not a local duplicate) assemble the 36-column tab-separated row, in the exact column order the destination spreadsheet expects; `ClientID` is left blank here — a placeholder, not a guess — since the backend assigns the real one (see below). `sanitize()` strips tabs/newlines from every value so the TSV can't be corrupted by free-text input.
- **On submit**, `ApoComm.registerClientRemote(values)` (shared, see "Shared Google Sheets backend" below) sends the row — still carrying the blank `ClientID` placeholder — to the backend's `registerClient` action, which allocates and returns the real ID. `#save-status` reports which happened: on success, `values.ClientID` is set to whatever ID the backend returned, the TSV output is filled in with that real ID, and the row is cached locally under it ("Saved as `<ClientID>` to the shared database — available to the other tools everywhere"). On a backend failure, `nextClientId()` generates the offline-fallback ID described above, the row is cached locally under *that* ID instead, and a `.warning`-styled message says so ("Could not reach the shared database — saved locally only..."). Either way, the TSV output and local cache are only ever written once a real (backend or fallback) ID is known — never under the blank placeholder. There is intentionally no Gmail integration here — see domain context below for where that logic lives conceptually.

### Site generator (`admin/site-generator/index.html`, `admin/site-generator/style.css`, `admin/site-generator/app.js`)

Takes one pasted 36-column TSV row (the same format the registration form produces) and generates a single self-contained HTML file — a one-page public site for that missionary.

- `parseRow()` splits on the first non-blank line, then on `\t`; it deliberately does not `.trim()` the whole line before splitting, since trailing empty columns (e.g. `Notes` blank) end the row in real tab characters that a blanket trim would eat, undercounting columns.
- `evaluateSecurityGate()` is the security gate, checked before anything is generated. **It fails closed**: only an explicit, recognized "no" (`NO`/`N`/`NON`/`FALSE`/`0`, via the shared `ApoComm.isSecuritySensitive()`) clears a profile. A blank cell, `OUI` typed into the French-headed Sheet, or any unrecognized value is treated as sensitive and blocks, with a distinct message naming the unreadable value rather than the generic "needs human review" text — the `apostello-onboarding` rule is in doubt, YES. (This previously compared against the literal string `"YES"` only, so `OUI` and an empty cell both generated and published freely.) Beyond that, `SecuritySensitive = YES` with empty `SecurityInstructions` blocks generation outright (no preview, no decision summary — nothing rendered). `YES` with instructions present generates the site but treats `SecurityInstructions` as an allow-list for `CountryOfService`/`CityOfService`, evaluated by `isLocationFieldAllowed()`.
- `isLocationFieldAllowed()` reads `SecurityInstructions` clause by clause (split on `.`/`;`/newline). A clause permits `country` or `city` only if it contains the keyword plus an explicit allow word (`ok`, `allowed`, `share`, `publish`, ...) with no negation word (`not`, `never`, `don't`, ...) in that same clause. Silence or ambiguity defaults to hidden — this is the safety-critical piece, so precision was favored over cleverness.
- `buildSiteHtml()` assembles the output document, escaping every interpolated value via `escapeHtml()` (the generated page is real HTML served to the public, so free-text fields like `MissionSummary` must not be able to inject markup/scripts). The `Email` field is never printed as visible text — only used inside a `mailto:` href behind a generic "Get in touch" / "Partner With Me" label.
- **The generated public site has its own visual identity, deliberately different from this admin tool's own "correspondence" styling (see "Shared visual identity" above) and from every other tool in the repo**: a bold editorial/industrial template — grayscale photography (`filter:grayscale(100%)` applied to `.photo-slot img`, so any real photo pasted in later is grayscaled automatically, not by hand), coral (`#E8623A`) and sage (`#5C6E5A`) color-blocked sections on a near-black/white base, heavy uppercase headlines (`--headline: 'Arial Black', ...` — a genuinely common system font rather than a webfont, since `SITE_CSS` still can't load external fonts; tight letter-spacing + uppercase does the "condensed" work instead), pill CTAs. Layout is split-screen rather than stacked-centered: a full-bleed hero (`.hero`) with the top bar (mark + one contact pill) overlaid directly on the photo, a 50/50 `.split` for About/Mission (photo one side, sage block the other), a full-width typographic `.statement` for Where I Serve, an asymmetric `.photo-band` (one large + two stacked slots) rather than a gallery grid, and a closing full-bleed `.cta-section` in coral with `MainObjective` itself as the headline. All of it collapses to a single stacked column under 760px (`.split` photo-on-top-block-below, `.photo-band` all slots full-width) — see `SITE_CSS`'s `@media` block.
- The photo section (`buildPhotoSection()`) plus the hero and About photos are five `.photo-slot` divs total (hero, about, and 3 in the photo band), each preceded by an HTML comment (`<!-- PHOTO n: replace... -->`). Each one renders a real `<img src="...">` when a photo has been assigned to that slot via the photo picker (see "Photo picker" below) — `photoSlotHtml(note, viewUrl)` takes an optional `viewUrl` and swaps in an `<img>` instead of the placeholder `<span>Photo</span>` when one is given, `escapeHtml()`-ing the URL same as every other interpolated value. A slot with nothing assigned still falls back to the original placeholder-div-plus-comment convention, so a client with no Drive photos yet (or a slot nobody assigned) still hands off cleanly to a human editing the downloaded HTML directly. The grayscale filter on `.photo-slot img` applies automatically either way.
- **The generated page is localized** (English/French) through a `SITE_TEXT` dictionary keyed by `ApoComm.detectLanguage(PrimaryLanguage)`, covering every visible label plus the `<html lang>` attribute: contact and CTA pills, "About Me", "Where I Serve", "Get Involved", the sent-by line and the footer. This tool previously had no localization at all and shipped English headings onto French pages. The hero mark drops the English possessive in French (`Claire · Apostello Comm` rather than `Apostello Comm × Claire's Site`), which has no clean French equivalent.
- `SITE_CSS` is inlined into the generated page's `<style>` tag so the output is a single portable file with no external requests (no font/CDN loads) — same constraint as before the template redesign, still honored.
- The generator UI shows a `security-decision` summary (SecuritySensitive value, and whether country/city will be shown) so a human can audit the gate's decision before trusting or publishing the output.
- After generation, a `save-path-instruction` line tells the operator exactly where to commit the file: `/sites/<ClientID>/index.html`. The download button's suggested filename is `index.html` to match — the browser can't write into a repo subfolder directly, so this is instructional text plus a conveniently-named download, not an automated commit.
- `toFirstPerson()` rewrites `MissionSummary`/`MainObjective` (which are typically captured in third person by staff — see `apostello-onboarding`) into first-person singular before they're shown on the public page, since the site is meant to read in the missionary's own voice. It's a deterministic rule-based pass (name/pronoun substitution, verb-form fixes for common auxiliaries), not NLP — good enough for the patterns this data actually contains, but a construction it doesn't recognize (e.g. the missionary's name as a verb's object with no preceding preposition) can slip through unconverted. Duplicated verbatim in the newsletter generator rather than shared, consistent with this tool's standalone generation logic. **English only, and now guarded as such**: every rule in it is an English auxiliary, pronoun or possessive, so on a French profile it produced "I accompagne des familles. Elle forme aussi des mères." (name swapped, verb unconjugated, later pronouns untouched) and "I veut faire passer son soutien" in the site's CTA headline. Both copies take the profile language as a fourth argument and return the text unchanged for anything but English. The consequence is deliberate and visible: a non-English profile keeps whatever person the missionary (or staff) wrote in, so a third-person `MissionSummary` now reads in the third person on a French page rather than in broken first person. Making it genuinely first-person in those languages needs per-language rules, not a wider regex.
- The client-search lookup (`#client-search`, see "Client lookup by name" below) is the one part of this tool that isn't standalone: it calls `ApoComm.searchClients()`/`ApoComm.fetchClientRow()` (shared, see "Shared Google Sheets backend" below) rather than reading `localStorage` directly, same as the newsletter/Instagram/intake tools.
- Once a client is selected via that search, `loadPhotos()` calls `ApoComm.fetchPhotos(clientId)` and renders the result as a `#photo-grid` of thumbnails (see "Photo picker" below) — this is the one tool of the three where a thumbnail carries a `<select>` (not a checkbox) letting the operator assign that specific photo to one of the 5 generated-site slots (`SLOT_LABELS`: hero, about, gallery 1–3); `slotAssignments` (a `{slotKey: viewUrl}` map, one photo per slot, kept in sync both ways when a photo is reassigned) is threaded through to `buildSiteHtml(fields, security, slots)` at generation time.
- Shares the registration form's visual identity (see "Shared visual identity" below): the raw generated HTML is tucked into a `<details>` disclosure so the confirmation screen leads with the `.preview-frame` (a small browser-chrome bar + the live `<iframe>`) rather than a wall of markup. The blocked-generation message (`evaluateSecurityGate()`'s `reason` string, local to this file, not shared) was reworded to the same calm tone as the registration form's security notice — the boolean gate logic itself is untouched.

### Monthly newsletter intake (`newsletter-intake/index.html`, `newsletter-intake/style.css`, `newsletter-intake/app.js`)

Short recurring form a missionary fills out each month. Beyond capturing the 10-column intake row, submitting this form now **automatically generates that month's newsletter and Instagram calendar in place** — no navigating to the other two tools, no manual paste. The raw TSV row is still shown after submit (for re-pasting into the standalone tools later, e.g. to regenerate a past month), but it's no longer the primary output.

- Fields: `ClientID`, `IsFirstNewsletter`, `Events` (list), `MeetingsSummary` (free text rollup, not itemized), `PrayerNeeds` (list), `UpcomingProjects` (list), `NumbersUpdate` (free text), `NewPhotoLinks`, `AnythingToAvoid`. `SubmissionDate` (today's date) is appended as a 10th, system-derived column, same reason as before (tells later intakes for the same `ClientID` apart).
- Required fields are `ClientID`, `IsFirstNewsletter`, and at least one `Events` entry — everything else is optional, so a very light month (one event, nothing else) is a valid submission, not an error.
- `Events`/`PrayerNeeds`/`UpcomingProjects` are variable-length lists: the missionary can enter any number of entries (including zero for the two optional ones), one per line or semicolon-separated — `sanitizeList()` normalizes either input style into a single `; `-joined TSV cell so the generators only ever have to split on `;`.
- `#client-search` above the `ClientID` field is the same name-based lookup combobox as the three admin tools (see "Client lookup by name" below) — selecting a name fills the `ClientID` field, which stays the field validation/submission actually reads. Missionaries who know their own Client ID (it's on their registration confirmation) can also just type it directly; the search box is a convenience, not a requirement, matching the fallback pattern used elsewhere.
- **On submit**, after the existing field validation passes: `ApoComm.fetchClientRow(ClientID)` (shared, see "Shared Google Sheets backend" below) looks up the matching registration row — backend `getClient` first, falling back to the local cache only if the backend is unreachable. This is what lets a missionary submit from a browser that has never talked to any Apostello Comm tool before, as long as the backend has their record. If no registration is found anywhere (backend genuinely has no such `ClientID`, and nothing local either), generation stops immediately with "No registration profile found for this client. Load or paste it first." — no newsletter, no Instagram calendar, no partial output from incomplete data. If found, the intake row is saved (`ApoComm.saveIntakeRemote()`, writing through to the backend's `saveIntake` action in addition to the local cache), then the security gate is evaluated against the registration row: `SecuritySensitive = YES` with empty `SecurityInstructions` blocks *both* outputs together — `nlSecurity.reason` (shared, unchanged) still drives the block/no-block decision, but the text actually shown to the missionary is a calmer, hand-written message local to this page's `app.js`, matching the registration form's softened security tone; nothing is generated for either channel either way. Otherwise `ApoComm.Newsletter.build()` and `ApoComm.Instagram.build()` (the latter wrapped in try/catch, since `checkLanguagePurity()` can throw) run back-to-back against the same `regFields`/`intakeFields`, and both results render on the same page in clearly separated "Newsletter" and "Instagram content calendar" sections, each with its own copy button(s) — see "Shared JS modules" below for where this generation logic actually lives.
- Single page, not a step wizard (too few fields to justify one) — fields are grouped into four `<fieldset>`s with serif `<legend>` headers ("This month", "Prayer", "Looking ahead", "Numbers & extras") matching the registration form's visual identity (see "Shared visual identity" below), each phrased as a natural question ("What happened this month that you'd want your supporters to know about?" rather than "Events"). No step indicator or progress bar.

### Newsletter generator (`admin/newsletter/index.html`, `admin/newsletter/style.css`, `admin/newsletter/app.js`)

Takes one 36-column registration row and one 10-column intake row, and drafts a plain-text subject + body for that month's newsletter, ready to paste into Mailchimp's Campaign Builder. All generation logic lives in `shared/newsletter-core.js` as `ApoComm.Newsletter` (see "Shared JS modules" below); this tool's own `app.js` is now just the client-search/month-select UI wiring (backend-first, via `ApoComm.searchClients()`/`ApoComm.fetchClientRow()`/`ApoComm.fetchIntakeMonths()`/`ApoComm.fetchIntakeRow()` — see "Shared Google Sheets backend" below) plus calls into `ApoComm.Newsletter.evaluateSecurityGate()` / `.build()`.

- Reuses the registration form's security gate concept (`ApoComm.evaluateSecurityGate()`, shared): `SecuritySensitive = YES` with empty `SecurityInstructions` blocks generation outright, same message as the site generator.
- Extends the site generator's clause-scanning allow-list (`ApoComm.isTopicAllowed()`, generalized from `isLocationFieldAllowed()`) to six topics: `intro` (the `MissionSummary`/`DepartureDate` used in a first newsletter), `highlights` (`Events`+`MeetingsSummary`), `prayer` (`PrayerNeeds`), `looking_ahead` (`UpcomingProjects`), `numbers`, and `whatsapp`. Each is included only if a `SecurityInstructions` clause explicitly permits it; otherwise the whole section is omitted (except `intro`/`whatsapp`, which swap to a fixed, non-specific line) rather than attempting any automated rewriting of the missionary's own words.
- Content is always exactly 4 fixed sections regardless of how many list items exist that month — "This Month's Highlights", "Prayer Needs", "Looking Ahead", "By the Numbers" — each skipped entirely (not padded) if its list is empty. `weaveItems()`/`buildSection()` weave any number of real list items (each kept verbatim after `ApoComm.toFirstPerson()`) into one flowing passage using a rotating bank of fixed lead-in connectors (`CONNECTORS`, e.g. "On top of that: ", "Around the same time: ") — never an itemized "first... second..." list. The anti-fabrication rule applies per *section*, not per item: real material is woven together first, and only if the section is still under `MIN_EXPANSION_WORDS` does the same generic reflection-bank top-up from before (now including a fourth, `looking_ahead` bank) kick in, with the same `FALLBACK_COMMENT` marker if a section still can't honestly reach 150 words.
- `ApoComm.applyAvoidList()` (shared) is a second, independent redaction pass that always runs, regardless of `SecuritySensitive`: it splits the intake's `AnythingToAvoid` into clauses and case-insensitively strips them from the assembled subject/body. Missionaries write this field as an *instruction* ("Ne pas nommer l'hôpital du district"), not as a bare term, so matching the clause verbatim found nothing and the named subject was published while the audit panel reported "not found in output". `ApoComm.avoidTermVariants()` now expands each clause into the candidates worth searching for: the whole clause, the subject left after an instruction prefix is stripped (FR/EN/ES/PT forms of "ne pas nommer / mentionner / parler de", "do not name / mention / publish", "no mencionar", …), and that subject without its leading article — longest first, so the article doesn't survive as an orphan. An elided French article left stranded by a removal (`l'` followed by whitespace, which is never valid French) is cleaned up afterwards. `applied[]` now carries a `matched` array naming which variant actually fired, so the audit panel can say what was removed rather than only whether something was. Still a literal-substring safety net, not an NLP filter: a paraphrase of the subject is not caught, and the prefix list is finite.
- Content and template chrome (labels, intro/CTA phrasing, sign-off) are localized to `PrimaryLanguage` via a small `TEMPLATES` dictionary (English and French only, detected by `ApoComm.detectLanguage()`, defaulting to English). The missionary's own free text is never machine-translated — only the surrounding scaffolding changes language. **Two languages only.** Spanish and Portuguese were removed: they had full newsletter chrome but only a generic one-template-per-format Instagram set, which looked finished and was not — anything that is not French now resolves to English. `detectLanguage()` accepts the English name, the endonym, and ISO codes with or without a region (`French`, `Français`, `fr`, `fr-FR`); it previously tested only the endonym stem `fran`, so `French` — the value an English-language form actually collects — fell through to English. The registration form now offers a two-way button choice instead of a free-text field (see below), so new rows carry exactly `English` or `French`; the looser matching stays for older rows and for values typed into the Sheet by hand.
- If the registration and intake rows carry different `ClientID`s, a non-blocking `mismatch-warning` banner fires — this doesn't block generation (unlike the security gate) since a human is expected to read and correct it before sending. (The automated intake flow can't hit this case: it looks up the registration row *by* the intake row's own `ClientID`, so the two can never disagree.)
- The `security-decision` panel lists, per topic, whether it was included or omitted, plus per-section word counts and which `AnythingToAvoid` terms were found and stripped — the same audit-before-publish pattern as the site generator.
- The whole newsletter reads in the missionary's own first-person voice: template chrome is hand-written in first person per language; every list item and free-text field is passed through `ApoComm.toFirstPerson()` before being woven in. Subject lines and the sign-off name are left as a name (third person there is expected — a reader needs to know whose update they're opening).
- Once a client is selected via the search, `loadPhotos()` fetches and renders that client's photos the same way as the site generator (see "Photo picker" below), but with checkboxes instead of a per-slot `<select>` — there's no layout to assign photos into here, just a monthly pool. Checking one or more writes their `viewUrl`s, comma-separated, into the `NewPhotoLinks` column (index 7) of the `#intake-input` TSV textarea via `applySelectedPhotosToIntake()`, auto-filling `ClientID` (column 0) from the registration row if that column is still blank. This doesn't add a new field or change the 10-column intake shape — it's just a faster way to fill in the same cell a human could otherwise type/paste into directly (which remains the fallback when there are no photos yet).

### Instagram content calendar generator (`admin/instagram-calendar/index.html`, `admin/instagram-calendar/style.css`, `admin/instagram-calendar/app.js`)

There was no prior "Instagram generator" in this repo — this tool was built from scratch to this spec. It reuses the exact same two inputs as the newsletter generator (36-column registration row + 10-column monthly intake row, no new form) and turns the monthly pool of real items into a 4-week, ~16-post Instagram calendar — a different format of the same material, not a separate content stream. All generation logic lives in `shared/instagram-core.js` as `ApoComm.Instagram` (see "Shared JS modules" below); this tool's own `app.js` is just UI wiring, including the same backend-first client-search/month-select pattern as the newsletter generator (see "Shared Google Sheets backend" below).

- Parsing, the security gate/`isTopicAllowed()`, `applyAvoidList()`, and `toFirstPerson()` are shared with the newsletter generator via `shared/apocomm-common.js` rather than duplicated (this was previously duplicated verbatim — see "Shared JS modules" below for why that changed). Four topics are gated here (`highlights`, `prayer`, `looking_ahead`, `numbers` — no `intro`/`whatsapp`, since this tool has neither); `MeetingsSummary` rides on the `highlights` allow-flag, same as in the newsletter.
- **The topic pool is dynamic, not fixed.** `buildItemsByCategory()` expands `Events`/`PrayerNeeds`/`UpcomingProjects` into one pool entry *per list item* (plus one entry each for `NumbersUpdate` and `MeetingsSummary` if present) — a month with 4 events and 3 prayer needs has 7+ distinct real topics to draw from, not 3. `buildPool()` interleaves categories round-robin so even the earliest slice of the calendar already mixes topics.
- `FORMAT_PREFERENCE` defines, per category, an ordered list of compatible formats out of the 7-format library. `prayer_focused` is the one hard exclusivity rule from the spec (prayer only); every other format is open to any category. Each pool item's list is also *rotated by its own index within the category* (`rotateList()`) — without this, every item in a multi-item category would share the same #1 format (four Events would all open with the identical "Behind-the-Scenes" framing text); rotating means four Events instead lead with four different formats.
- `buildWaves()` is the scheduler: wave 0 gives every distinct pool item its own single best-fit format (maximum variety first — this is "draw from the expanded real pool before falling back to multiple-angle recycling"), wave 1 gives items that still have an unused format a second angle, and so on. Target is `min(16, wave count)`; a richer month (more real items) fills more of the calendar straight from wave 0, so it reads as more varied, not more repetitive. If waves run out before 16 slots are filled, the shortfall is real and the output ends with `<!-- Topic exhausted without fabrication risk -->` instead of padding or recycling further — verified by a test that limits input to a single Event (capacity 6) and confirms the flag fires at exactly 6 posts.
- Caption templates (`TEMPLATES.english`, keyed by category then format) never introduce a new fact, number, name, date, or event — each one wraps the missionary's own unaltered (already first-person) sentence in fixed framing text. `meetings` reuses the `numbers` template set (both are single rollup stats) rather than duplicating near-identical content. French now carries the same per-category set as English rather than the generic fallback it had before: with one template per format shared across every category, four Events in a month all opened with the identical framing sentence in French while English got four distinct angles. `GENERIC_TEMPLATES` is gone, and `getCaption()` reads `TEMPLATES[lang][category][format]` for both languages, falling back to the English set for an unknown language.
- `checkLanguagePurity()` is a defensive per-post check run before a caption is ever added to the calendar: for an English profile it rejects any generated caption whose *template-authored framing* (the missionary's own seed sentence is deliberately excluded from the check, isolated via `caption.split(seed)`) contains non-English accented characters; for a non-English profile it rejects stray English telltale phrases. `detectLanguage()` already reads `PrimaryLanguage` from the parsed registration row and nothing else — there is no code path through which session or conversation context could influence it — so this check exists as a regression guard, not a fix for a located bug.
- `GRAPHIC_NOTES` and `HASHTAG_BANK` are keyed by format/category only, not language — both are either operator-facing instructions (graphic direction) or hashtags that conventionally cross language boundaries on Instagram regardless of caption language, so one English set is reused everywhere rather than translating four times.
- Output renders as both a visual calendar (`calendar-view`, grouped by week, one card per post showing topic label — e.g. "Event 2", "Prayer Need 1" — format/caption/hashtags/graphic note) and a plain-text export (`calendar-output`) for pasting into a planner; `AnythingToAvoid` is applied per-caption so both views stay consistent, and the `security-decision` panel lists posts generated vs. target, pool size, which formats were used per category, and any avoid-list terms stripped.
- Photo picker wiring is identical to the newsletter generator's (checkboxes → comma-separated `viewUrl`s → `NewPhotoLinks` in `#intake-input`, see "Photo picker" below and the newsletter generator bullet above) — this tool has no photo slots of its own to assign into, since the Instagram calendar is text/caption output, not an HTML layout.

## Shared JS modules (`/shared/`)

The newsletter generator, Instagram calendar generator, and the newsletter intake form's automated dual-generation flow all need the same generation logic (registration/intake TSV parsing, the security-gate clause-scanner, `AnythingToAvoid` redaction, first-person conversion, language detection, HTML escaping, and the shared-localStorage client lookup), plus each generator's own topic set and build routine. Rather than a fourth copy-paste (or asking the intake page to reach into the standalone tools' `app.js` files), this logic was extracted into three plain `<script>`-loaded modules — no bundler, no build step, consistent with the rest of this repo — each attaching to a single global, `window.ApoComm`:

- `shared/apocomm-common.js` — tool-agnostic infrastructure: `ApoComm.REG_COLUMNS`/`INTAKE_COLUMNS`, `ApoComm.parseRow()`, `ApoComm.evaluateSecurityGate(regFields, topics)` (the clause-scanning blocking decision, generalized to take a `{topicKey: [keywords]}` map so callers with different topic sets share one implementation — see below), `ApoComm.isTopicAllowed()`, `ApoComm.applyAvoidList()`, `ApoComm.toFirstPerson()`, `ApoComm.detectLanguage()`, `ApoComm.escapeHtml()`, the local-cache functions (`ApoComm.listSavedClients()`, `ApoComm.getSavedClientRow()`, `ApoComm.listSavedMonths()`, `ApoComm.saveIntakeRow()`, `ApoComm.cacheClientRow()`), and the backend-first orchestration layer built on top of them (`ApoComm.searchClients()`, `ApoComm.fetchClientRow()`, etc.) — see "Shared Google Sheets backend" below for that whole layer.
- `shared/newsletter-core.js` — everything newsletter-specific, exposed as `ApoComm.Newsletter`: its 6-key `TOPICS` map, `evaluateSecurityGate()` (a thin wrapper calling the common one with `Newsletter.TOPICS`), the four-language `TEMPLATES`/`EXPANSION_BANKS`/`CONNECTORS` dictionaries, paragraph weaving/expansion, and `build(regFields, intakeFields, security)` — the core generator, unchanged in behavior from before the extraction.
- `shared/instagram-core.js` — everything Instagram-specific, exposed as `ApoComm.Instagram`: its 4-key `TOPICS` map, `evaluateSecurityGate()`, the format/caption/hashtag libraries, `checkLanguagePurity()`, the pool/wave scheduler, `build()` (the core generator), `renderHtml()`/`renderText()`, and `showDecisionLines()` (returns the audit-panel HTML lines as an array rather than writing to a specific DOM node, since the standalone tool and the intake page each have their own `security-decision` element to fill).
- Both `admin/newsletter/index.html` and `admin/instagram-calendar/index.html` load `apocomm-common.js` then their own core module before `app.js`; `newsletter-intake/index.html` loads all three (it needs both generators). Each tool's own `app.js` now contains only DOM wiring (client-search combobox, month-select, form/button handlers) and calls into `ApoComm.*`/`ApoComm.Newsletter.*`/`ApoComm.Instagram.*` — no generation logic is duplicated in any `app.js` anymore. The registration form and site generator are unchanged and still fully standalone (out of scope for this extraction — they don't share a topic-gated generator with anything else).
- Generalizing `evaluateSecurityGate()` to accept a `topics` parameter (rather than two separate hardcoded copies) is what lets the intake form's automated flow check the block/no-block decision once and have it apply identically to both outputs: the decision itself (`SecuritySensitive`/`SecurityInstructions` on the registration row) never depends on which topic set is passed in, only each generator's per-topic *allow* map does — so `Newsletter.evaluateSecurityGate()` and `Instagram.evaluateSecurityGate()` always agree on blocked/not-blocked for the same registration row, even though they're called separately to get their differently-shaped allow maps.

## Shared Google Sheets backend

All 5 tools talk to one shared Google Sheet (client records in a "Fiches" tab, monthly intakes in a "Monthly_Intakes" tab) through a small Apps Script Web App, rather than each browser only knowing what's been saved locally. `localStorage` is no longer the source of truth — it's now purely an **offline fallback cache**: every write goes to both the backend and the local cache, and every read tries the backend first and only falls back to the local cache if the backend is unreachable.

- `shared/apocomm-config.js` — the single place the Web App URL and API key are configured (`ApoComm.CONFIG.WEB_APP_URL` / `ApoComm.CONFIG.API_KEY`). Every tool loads this before `apocomm-backend.js`; nothing else in the codebase hardcodes either value.
- `shared/apocomm-backend.js` — `ApoComm.Backend`, a thin GET-only client for the seven actions (`searchByName`, `getClient`, `registerClient`, `getIntake`, `saveIntake`, `listIntakeMonths`, `listPhotos`) — this API has no POST; writes are GET requests carrying a URL-encoded JSON array in a `data` param. Every function resolves to `{ok, ...}`; `ok: false` means a genuine transport failure (network error, non-2xx HTTP, unparseable body) — reachable-but-empty/not-found responses (`null`, `[]`, `{error: ...}`, etc.) resolve as `ok: true` with an empty/null payload instead, so callers can tell "the database is down" apart from "the database has no such record" (see `looksEmpty()`/`asRow()`/`asList()` in that file). `registerClient` sends the row with a *blank* `ClientID` placeholder (`Object.assign({}, regFields, {ClientID: ""})`, never the caller's own value) since **ClientID allocation is the backend's job, not the client's** — the response is expected to carry back the real, assigned ID (a bare string, the echoed row with the ID in the first slot, or an object under a `clientId`/`ClientID`/`id` key — see `extractClientId()`); a response with no extractable ID is treated as a failure, since the caller has nothing usable to save under. **This module could not be exercised against the real deployed backend while writing it** — this sandbox's network egress policy blocks `script.google.com` outright — so its response-shape handling is written defensively against what the API description implies (bare JSON array for a single row, bare array of rows for a list) with tolerance for a few common envelope variations; if the live backend's actual shape differs, `looksEmpty`/`asRow`/`asList`/`entryToRegFields`/`extractClientId` are the functions to adjust; every caller elsewhere in the codebase consumes the already-normalized `{ok, ...}` result and shouldn't need to change. Every request/response pair is logged to the browser console (`console.log`, prefixed `[ApoComm.Backend]`) — the outgoing action/params plus a masked API key (first 4 characters + length, so a copy-paste key mismatch is diagnosable without printing the real key), and the raw HTTP status + response body text on the way back, logged *before* attempting to parse it as JSON — so a misconfigured deployment (wrong key, HTML/login-page response instead of JSON, an Apps Script `{"error": "..."}` body riding on an HTTP 200) is visible in the console rather than silently collapsing into "the warning didn't show, why not." Write actions (`registerClient`/`saveIntake`) always treat a `.error` field in an otherwise-200 response as a failure — an HTTP-200-with-error-body is a documented Apps Script Web App quirk, not a real success, and both `#backend-warning` and the registration form's `#save-status` need to reflect that, not silently proceed as if the write landed.
- `shared/apocomm-common.js` adds the orchestration layer on top: `ApoComm.searchClients(query)`, `ApoComm.fetchClientRow(clientId)`, `ApoComm.registerClientRemote(fields)`, `ApoComm.saveIntakeRemote(intakeFields)`, `ApoComm.fetchIntakeMonths(clientId)`, `ApoComm.fetchIntakeRow(clientId, month)` — each tries the backend first, refreshes the local cache on a successful read, and falls back to the local cache (with `warning: "Could not reach the shared database — using local data only."`) only on a genuine transport failure. `ApoComm.searchClients()` additionally falls back to the local cache when the backend is reachable but returns zero matches (this browser may hold a client registered while offline that hasn't synced yet). `ApoComm.registerClientRemote(fields)` is the odd one out: since `fields.ClientID` going in is only ever a placeholder, there's nothing to cache locally until the backend responds — on success it resolves `{ok: true, clientId}` with the real ID already cached under `ApoComm.cacheClientRow()`; on failure it resolves `{ok: false, clientId: null, warning}` and deliberately does **not** invent a fallback ID itself, leaving that policy to the caller (see the registration tool below). Also here: `ApoComm.regFieldsToBackendRow()`/`backendRowToRegFields()` and `ApoComm.intakeFieldsToBackendRow()`/`backendRowToIntakeFields()` convert between the `fields` object every generator already works with and the backend's JSON-array row shape; `ApoComm.cacheClientRow()` writes the local TSV cache (called after every successful backend read/write with a *real* ClientID, so the cache never goes stale while the backend is reachable, and never gets polluted with a placeholder key); `ApoComm.BACKEND_INTAKE_COLUMNS` is the backend's 11-value intake row shape — the same 10 local `INTAKE_COLUMNS` plus an explicit `Month` (`YYYY-MM`, derived from `SubmissionDate`) column, since that's what `getIntake`/`listIntakeMonths` index by.
- Every tool's UI layer calls these orchestration functions instead of reading `localStorage` directly, and shows `result.warning` (when present) in a `#backend-warning` element styled consistently across all 5 tools' stylesheets. Client-search results and the "load a past month" selects are rendered asynchronously with a request-token guard (`searchToken`/`monthToken`, incremented per call, stale responses discarded) so a fast typist or fast client-switch never has an old response clobber a newer one.
- The registration form's `nextClientId()` (the `APC-YYYY-000` counter) is now purely an **offline-only fallback** — used only when `ApoComm.registerClientRemote()` resolves `ok: false`, so a registration submitted with no connectivity still has something to display/cache under rather than being lost. Two browsers registering offline in the same year can in principle generate the same fallback `ClientID` before either syncs; an accepted limitation of a purely local counter, scoped to the already-degraded offline path, not something designed around here.
- **Verifying this against the real backend**: this environment could not reach `script.google.com` to test live, so integration correctness was verified by mocking `ApoComm.Backend`'s HTTP calls (Playwright `page.route()`) against an in-memory fake "sheet" shared across separate browser contexts — covering: registration write-through with the backend assigning the ClientID (confirming the row sent carries a blank placeholder and the displayed/cached ID matches whatever the mock returned, including across two consecutive registrations getting two different server-assigned IDs), the offline-fallback path when the backend is unreachable, a fresh browser (empty `localStorage`) finding and loading a client by name, the full intake→dual-generation flow using only backend data, backend-down fallback-with-warning, a genuinely-unregistered `ClientID` producing the clean "not found" message without a false connectivity warning, and the security-block case sourced entirely from backend data. All passed against the mocked contract; the real deployment should be smoke-tested against these scenarios before relying on it.

## Shared localStorage across tools

All 5 tools are served from the same GitHub Pages origin, so `localStorage` is naturally shared between them in a given browser. Since the Google Sheets backend integration above, this is no longer the source of truth for client/intake data — it's an **offline fallback cache**, kept warm by every successful backend read and write (see "Shared Google Sheets backend" above) and consulted only when the backend can't be reached. Two key conventions, used consistently across `registration`, `admin/site-generator`, `admin/newsletter`, `admin/instagram-calendar`, and `newsletter-intake`:

- `apocomm_client_<ClientID>` — a cached 36-column registration TSV row. Written by `ApoComm.cacheClientRow()` after any successful `registerClient` write or `getClient`/`searchByName` read. Manual TSV paste still works exactly as before on the three admin tools that have a textarea — the lookup (backend or cache) is a convenience, not a requirement.
- `apocomm_client_<ClientID>_intake_<YYYY-MM>` — a cached 10-column monthly intake row, keyed by month. Written by `ApoComm.saveIntakeRow()`, called both directly (as the local half of `ApoComm.saveIntakeRemote()`, from the newsletter/Instagram/intake tools right after a save) using the intake row's *own* `ClientID`/`SubmissionDate` (not necessarily whatever is currently in the registration textarea, in case of a `mismatch-warning`). The newsletter/Instagram tools' "Load a past month's intake" `<select>` is populated via `ApoComm.fetchIntakeMonths()` (backend `listIntakeMonths`, merged with any local-only months) whenever the registration textarea changes (`regInput.addEventListener("input", refreshMonthSelect)`).
- The client-id scan (`ApoComm.listSavedClients()`, the local-only half of `ApoComm.searchClients()`) explicitly excludes any key matching `..._intake_\d{4}-\d{2}$` so a saved intake month never shows up masquerading as a client — this is also why `nextClientId()`'s counter key lives outside the `apocomm_client_` namespace entirely (see above); a bug where it briefly didn't caused a bogus `"seq_2026"` entry to appear in every "load saved client" list.
- None of this touches generation logic or security gates — it only pre-fills the same textareas/fields a human would otherwise paste into by hand, so every existing security/validation path runs unchanged regardless of whether the input came from the backend, the local cache, or a manual paste.

### Client lookup by name (site generator, newsletter, Instagram, newsletter intake)

The raw `ClientID` (`APC-YYYY-000`) stays the canonical key everywhere it matters (storage keys, the Sheet, the `apostello-onboarding` skill) but is never shown to the operator (or, on the intake form, the missionary) in these four tools — they search and select by name instead.

- `#client-search` is a text input, not a `<select>`: `ApoComm.searchClients(query)` (shared, backend-first — see "Shared Google Sheets backend" above) resolves to `{clients, source, warning, tooShort}`, where each client is a `{clientId, firstName, lastName, country, label}` object. **A query shorter than `ApoComm.SEARCH_MIN_CHARS` (2) is refused without a network call** and resolves `{clients: [], tooShort: true}`. Focusing the empty input used to search with an empty query and list everyone; the backend's `searchByName('')` matched every row, so three characters of URL returned the whole client base, and it now requires two characters and caps at 25 results. The two constants are positional twins — keep `ApoComm.SEARCH_MIN_CHARS` in step with `SEARCH_MIN_CHARS` in `backend/apocomm_backend.gs`. Every tool's `renderClientResults()` checks `result.tooShort` first and shows a "type at least N letters" hint; without that check the empty result falls through to "No saved clients yet", which tells an operator with a full database that it is empty. Typing re-searches live. This is async now (a network call, not a synchronous local read), so every tool's `renderClientResults()` shows a transient "Searching…" placeholder and guards against out-of-order responses with an incrementing `searchToken` — matching `renderClientResults()`, still duplicated per tool since each tool's DOM/result-wiring is slightly different (three fill a TSV textarea; the intake form fills the `ClientID` input directly).
- `ApoComm.assignDisambiguatedLabels()` (exported from `apocomm-common.js` so both the local-cache path and backend-sourced results share it) groups clients by identical "First Last" and appends a disambiguator only when needed: `(Country)` if every client in the group has a distinct, non-empty country, otherwise `(last 4 chars of ClientID)` as a guaranteed-unique fallback (e.g. two same-named clients in the same country).
- Selecting a result never trusts whatever the search step returned as the full record — it always calls `ApoComm.fetchClientRow(clientId)` (backend `getClient` first) to get the authoritative current row, per the explicit requirement that a stale/lighter search result shouldn't be what ends up driving generation. In the site generator/newsletter/Instagram tools this fills the registration textarea; on the intake form there's no textarea to fill — selecting a result instead writes `client.clientId` straight into the `#ClientID` field (the field the form actually validates/submits) and shows the label in the search box. In every case the actual `ClientID` only ever travels internally via a `clientMap` closure keyed by ID (never round-tripped through a DOM attribute as raw TSV, to avoid tab-character escaping edge cases).
- Two empty-state messages guide the user instead of a blank list: "No saved clients yet" (backend/cache has nothing at all) vs. "No match" (clients exist, none match the query) — both point at the fallback path (pasting the registration TSV row directly into the textarea below, on the three admin tools; typing the Client ID directly into the field below, on the intake form).

### Photo picker (site generator, newsletter, Instagram)

Each client's Drive folder (set up manually per client — there's no upload pipeline in this codebase; a missionary uploads their own photos and someone shares the folder) is browsable from three tools via the `listPhotos` backend action, surfaced as a thumbnail grid once a client is resolved through the name search above. The newsletter-intake form and registration form are **not** part of this — the intake form keeps its plain `NewPhotoLinks` text input, and registration doesn't touch photos at all.

- `Backend.listPhotos(clientId)` (in `apocomm-backend.js`) follows the same GET/normalize pattern as every other read action: reachable-but-empty resolves `{ok: true, photos: []}`, a genuine transport failure resolves `{ok: false, photos: []}`. `entryToPhoto()` normalizes each entry defensively (same "could not test against the real backend" caveat as the rest of this file) — tolerating a bare URL string or an object under `viewUrl`/`url`/`link`/`webViewLink`; an entry with no extractable URL is dropped rather than rendered as a broken thumbnail. `ApoComm.fetchPhotos(clientId)` (in `apocomm-common.js`) is the thin orchestration wrapper every tool actually calls — unlike the client/intake orchestration functions, there's no local-cache fallback here (photos were never cached locally to begin with), so a transport failure just means an empty grid plus the usual `#backend-warning` text.
- The fetch is triggered from each tool's `selectClient()` — specifically, only when a client is picked **through the name search**, not on a manual TSV/textarea paste (a manual paste has no resolved `ClientID` to key `listPhotos` on until the operator effectively re-selects by search). `loadPhotos(clientId)` guards against out-of-order responses with an incrementing `photoToken`, same convention as `searchToken`/`monthToken`.
- **Empty state**: if `listPhotos` comes back with zero photos, the grid is replaced with a single calm line — "No photos yet — the missionary can upload to their Drive folder, or paste a link below" — and the tool's existing manual fallback (the TSV/intake textarea, which already carries `PhotosLink`/`NewPhotoLinks` as one of its columns and can be typed/pasted into directly) is left completely untouched. Nothing about the photo picker ever removes or disables that manual path — it's additive UI only.
- **Security gate is not touched.** Thumbnails render regardless of `SecuritySensitive`, on the reasoning that the real access-control decision already happened when the client's Drive folder was set to private and a human chose what to put in it — `evaluateSecurityGate()`'s blocking logic (registration/site-generator/newsletter/Instagram, all four) is unmodified by this feature. The only concession to a `SecuritySensitive = YES` profile is a small non-blocking `.photo-thumb-sensitive` label on every thumbnail reading "Confirm this is cleared for public use" — a soft nudge, not a second gate.
- **Site generator** (`admin/site-generator/app.js`): each thumbnail carries a `<select>` (`SLOT_LABELS`: hero, about, gallery 1–3) rather than a checkbox, since the picked photo has to land in one specific spot on the generated page. `slotAssignments` is a `{slotKey: viewUrl}` map kept one-photo-per-slot: choosing a slot for a photo clears that slot from any other photo currently holding it (and resets that other thumbnail's dropdown back to "Not used"). `buildSiteHtml(fields, security, slots)` threads this through to `photoSlotHtml(note, viewUrl)`, which renders a real `<img src="...">` (through `escapeHtml()`) in place of the placeholder `<span>Photo</span>` wherever a slot has an assignment, and falls back to the original placeholder-plus-comment convention for anything left unassigned.
- **Newsletter and Instagram calendar** (`admin/newsletter/app.js`, `admin/instagram-calendar/app.js` — identical wiring in both, not shared into a common module since the rest of each tool's DOM wiring is already duplicated per-tool by convention, see "Client lookup by name" above): each thumbnail carries a checkbox instead, since any number of photos can be used in a given month's content. Checking/unchecking calls `applySelectedPhotosToIntake()`, which writes the checked photos' `viewUrl`s — comma-separated — into column index 7 (`NewPhotoLinks`) of the `#intake-input` TSV textarea, padding the textarea to 10 columns and auto-filling `ClientID` (column 0) from the registration textarea if it's still blank. This is purely how that one cell gets filled in faster — the 10-column intake shape, and the fact that a human can still type/paste directly into that textarea, are both unchanged.

## Domain context

Apostello Comm is a communications agency serving missionaries. Client (missionary) records live in a Google Drive spreadsheet ("Apostello Comm — Base Missionnaires"), not in this repository. Operational rules for handling missionary client data (record format, required fields, security handling for missionaries in restricted-access countries, email drafting rules) are defined in the `apostello-onboarding` skill available in this environment — invoke it for any task involving missionary contacts, client records, or missionary-facing content, rather than improvising the process here.
